# 実装できることしか名乗らせない

Tsuuchi で踏んだ設計の失敗と、その直し方。**通知アプリに限らず効く。**

## 何が起きたか

パーサーが「このリクエストは監視可能か」を `feasibility`（api / public / needs_info / blocked）
で判定していた。46 件のテスト表まであり、判定自体は正しかった。

ところがサーバーの巡回処理は、`symbol`（実価格）か `url`（ページ差分）を持つものしか見ていなかった。
突き合わせたら **23 ジャンル中 9 件が「監視できます」と名乗りながら、一度も巡回されていなかった。**

最悪だったのは「楽天の株が800円を切ったら」で、**`feasibility: 'api'`（＝公式データで確実）と
申告しながら、銘柄辞書に無いので `symbol` が付かず、永遠に発火しない。**

ユーザーから見ると「見てるよ」と言われ続けて何も来ない。レビューで一番嫌われる壊れ方。

## なぜ起きたか

**2 つの別概念を 1 つのフィールドで表していた。**

| | 意味 | 変わるタイミング |
| --- | --- | --- |
| 原理的に可能か | 公開ページを見れば分かるか | ほぼ変わらない |
| **今の実装で届くか** | 実際に巡回する手がかりがあるか | 実装が進むたび変わる |

前者だけを持っていると、実装が追いつく前に「できます」と言ってしまう。
**「原理的にできる」は、ユーザーへの約束にしてはいけない。**

## 直し方

原理的な判定は触らず（テスト表が定義している意味を壊さない）、
**実装の実態を表すフィールドを別に足す。**

```ts
export type Coverage = 'live-data' | 'page-diff' | 'needs-url' | 'unsupported'

/** 実装が実際に何をできるかだけから導く。願望を混ぜない */
export function coverageFor(w: Pick<Item, 'coverage' | 'symbol' | 'url' | 'feasibility'>): Coverage {
  if (w.coverage) return w.coverage          // 保存済みを優先
  if (w.feasibility === 'blocked') return 'unsupported'
  if (w.symbol) return 'live-data'
  if (w.url) return 'page-diff'
  return 'needs-url'
}
```

守るべき点が 3 つある。

**1. 導出元は実装の分岐条件そのものにする**

`coverageFor` が見ているのは、サーバーの巡回処理が分岐に使っているフィールドと同一。
「たぶんできるはず」が混入する余地を作らない。

**2. 不変条件をテストで固定する**

ジャンルを足したときに、また過大申告に戻るのを防ぐ。

```ts
it('symbolもURLも無いものが live-data / page-diff を名乗らない', () => {
  for (const input of samples) {
    const d = parse(input)
    if (d.coverage === 'live-data') expect(d.symbol).toBeTruthy()
    if (d.coverage === 'page-diff') expect(d.url).toBeTruthy()
  }
})
```

**3. 古いデータのために導出する。既定値に倒さない**

フィールドを後から足すと、既存データには入っていない。
`w.coverage ?? 'needs-url'` と書くと、**URL 設定済みのものまで「未設定」扱いになる。**
実際にこれをやって、詳細画面に URL 入力欄が出続けるバグを作った。

同じ理由で、保存先を変えたときは移行も要る。Tsuuchi では URL が表示用フィールドにしか
入っていなかったので、機械可読なフィールドへ移す SQL を書いた。
**これを忘れると、既存ユーザーだけ永久に動かない。**

## 表示まで通す

内部で正しく分類しても、ユーザーに見えなければ意味がない。

- 登録**前**の確認画面に「何をどこまでやるか」を出す（作ってから気づかせない）
- 詳細画面にも出す（「これ、いつ届くの？」を確かめる場所）
- **一次情報を 1 ファイルに置き、アプリ内文言・サポートページ・ストア説明文を
  すべてそこから書く。** 実装より広く書かない、を運用ルールにする
